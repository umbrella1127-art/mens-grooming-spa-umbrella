# HPB分析（集客KPI基盤） — 運用ガイドと分析原則

ホットペッパービューティー（HPB）の月次実績（Salon Report PDF）を分析し、
戦略立案・レポート・Discord通知までを13体のサブエージェントで自動化する仕組み。
データは Supabase Postgres（サイトと同じDB）、画面は管理画面 `/admin/kpi` 配下。
店舗は `stores` テーブルに登録して増やせる（末尾「規約」の「他店舗の追加」）。

## ★ 最重要の前提：新規集客が目的

ホットペッパーは **新規客を獲得するための広告投資**。
全体の予約数・売上でROIを見ると既存客の来店タイミングでブレるため、
**すべての評価の主軸は新規側の指標に置く**。全体の数字は参考として併記する。

| 主軸となる指標 | 計算 |
|---|---|
| 新規獲得数 | `customers_new` |
| **新規獲得単価（CPA）** | `plan_cost_yen ÷ customers_new` |
| 新規率 | `customers_new ÷ net_reservations` |
| 初回回収率 | `新規客単価 ÷ CPA`（1.0超で初回来店だけで掲載料を回収） |
| 新規ROI | `新規売上 ÷ 掲載料` |
| 新規リピート率 | `new_repeat_rate` |

掲載プランの費用は店舗ごとに `stores.plan_cost_yen`（`scripts/hpb/config.json` → `db_migrate.py`）に設定する。
請求書で確認できるまでの暫定値は `plan_cost_note` に経緯（いつの時点の暫定値か、何を確認すれば確定するか）
を必ず書き残す。確定・変更したら `config.json` を更新し `db_migrate.py` を再実行すること。

## アーキテクチャ

```
          ┌─ Supabase Postgres ─ 全エージェントの共有記憶 ──────────────┐
          │  hpb_* (KPI / ブログ / 特集 / クーポン / スタイル / 競合)      │
          │  findings / strategies / strategy_options / page_observations │
          │  analysis_methods / analysis_runs / agent_tasks / analysis_reports │
          └───────────────────────────────────────────────────────────────┘
                                   ▲ 実行前に必ず参照（scripts/hpb/*.py 経由）
   /hpb-run → hpb-orchestrator（司令塔・自分では分析しない）
                 │
                 ├─ hpb-collector          集計          PDF/CSV → DB
                 ├─ hpb-page-scout         実ページ調査  実際の画面 → page_observations
                 │
                 ├─ hpb-analyst-funnel     新規をどこで失っているか ┐
                 ├─ hpb-analyst-retention  獲った新規は残るか        │ 並列
                 ├─ hpb-analyst-market     市場での位置とプラン      │ → findings
                 ├─ hpb-content-analyst    どのコンテンツが効いたか ┘
                 │
                 ├─ hpb-strategist-price     いくらにすると何人来るか ┐並列
                 ├─ hpb-strategist-creative  名前と見せ方で取れるか   │ 各3案
                 ├─ hpb-strategist-ops       現場の手順で取れるか     │ → strategy_options
                 ├─ hpb-strategist-page      実ページのどこを直すか   ┘
                 ├─ hpb-strategist           どれをやるか（採点・採用）→ strategies
                 │
                 └─ hpb-reporter           レポート → analysis_reports → 管理画面 + Discord通知
```

**1人1役**が原則。1つのエージェントに複数の問いを持たせない。
分析担当は自分の担当手法だけを実行し、担当外の切り口は完了報告で該当担当へ引き継ぐ。
戦略統合担当は**自分で案を考えない**（作る人と選ぶ人を分けるため）。

## ★ 共有記憶の原則（DBが全員の脳みそ）

13体のサブエージェントは互いに会話しない。つながっているのはDBだけ。
そのため全員が例外なく次を守る:

1. **行動する前に、必ずDBを読む** — `python scripts/hpb/context.py`（対象エージェントは `--for <agent>` を付ける）
2. **行動したら、必ずDBに書く** — findings / strategies / strategy_options / page_observations 等
3. **作業の最初と最後に、必ずチーム全員へ「今の状態」を書く** —
   ```bash
   python scripts/hpb/agent_checkin.py start --agent <agent> --run-id <run_id> --note "..."
   # …作業…
   python scripts/hpb/agent_checkin.py done  --agent <agent> --run-id <run_id> --note "..."
   ```
   これが管理画面の「今誰が動いているか」「いつ何をしたか」のタイムラインの唯一のソース。
   チェックインを忘れると、その担当は永久に「稼働中」のまま表示される。

オーケストレーターは委譲するすべてのエージェントに `run_id` を渡す責任を持つ。

## 毎月の運用（PDCAを月2回転させる）

**① 月の中頃（15日前後）— 中間チェック `/hpb-midcheck`**
Salon Report を途中でDLして `data/hpb/<store>/inbox/` へ → 新規獲得のペースだけ見る。
平年を下回っていれば**月内に手を打つ**（クーポンの並び替え・表示名変更なら即日効く）。

**② 最終木曜の翌日 — 月次フル分析 `/hpb-run`**
Salon Report（＋四半期に1回はリボン）を inbox に入れて実行。
Discordに新規数・CPA・課題・施策のサマリと管理画面のレポートURLが届く。

**③ 確認**
管理画面 `/admin/kpi`（集客KPIハブ）→ `/admin/kpi/hpb`（HPB詳細）→ `/admin/kpi/hpb/<月号>`（月次レポート）。

> 中間チェックの値は**確定値ではない**ので `hpb_kpi_snapshots` に入れ、`hpb_monthly_kpi` には混ぜない。
> 締め前の部分データを確定月と直接比べると必ず読み違える（`scripts/hpb/pace.py` が同日数比較を行う）。

## スケジュール

- 月次分析の実行日は「月の最終木曜の翌日（金曜）」。`python scripts/hpb/schedule_check.py --next` で次回日を確認できる
- PDF解析と pdfplumber が必要なため、実行は**このPCのClaude Codeから**行う（クラウドのスケジュール実行では動かない）

## 通知

`scripts/hpb/notify.py send` がサイトのDiscord Bot（`DISCORD_BOT_TOKEN`）で
`DISCORD_CHANNEL_KPI`（無ければ `DISCORD_CHANNEL_NOTICE`）へ要約＋レポートURLを送る。
送信結果は `notifications` テーブルに残る。未読管理は管理画面側で行う。

## 分析が育つ仕組み

`analysis_methods` テーブルが分析手法のレジストリ。
分析担当は毎月「もっと良い切り口はなかったか」を自問し、思いついたら手法として登録する。
`backfill_needed=true` を立てると `/hpb-backfill` が過去月へ遡って適用し、過去データの解釈も更新される。

戦略側は `strategies` テーブルで提案→実行→効果検証のループを回す。
**戦略担当は新提案より先に必ず前回提案の効果検証を行う。**

## 戦略は「1案」ではなく「3スタンス×複数論点」で出す

価格・訴求・運用・実ページの4担当が、それぞれ担当する論点ごとに

| スタンス | 位置づけ |
|---|---|
| `conservative`（守り） | 追加の負担がほぼ無い。確実に回るが伸びは小さい |
| `standard`（標準） | 現実的な本命 |
| `aggressive`（攻め） | 伸びは大きいがリスクあり。**撤退条件が必須** |

の3案を `strategy_options` に登録する。統合担当が
**効き幅／コスト／リスク／速さ**の4軸で採点し、論点ごとに1つ選ぶ。

- **落とした案も理由つきでDBに残す。** 後から判断をやり直せるようにするため
- **攻めの案を最低1つは撤退条件付きで採用する。** 守りだけ選ぶと市場平均に埋もれる
- **同じ論点で複数スタンスを同時採用しない。**

## ★ レポートだけ見て戦略を立ててはいけない

Salon Report は「クーポンが何本」「クリックが何件」という**数**しか教えてくれない。
お客さんが実際に判断材料にしているのは**そこに何と書いてあるか**で、そこはレポートに出てこない。

実ページ（`https://beauty.hotpepper.jp/sln<hpb_cd>/`）を確認すると、レポート上の前提と実態がズレていることがよくある:

- 口コミの最新投稿日がレポートの「口コミN件」という件数だけでは分からず、実は数ヶ月止まっている
- 分析対象にしていた月号のクーポンが、実ページではすでに価格・表示名ごと入れ替わっている
- クーポン本数の中に価格の無い見出し用ダミー行が混じっていて、本数を過大に数えている
- ブログの投稿頻度がレポートの集計期間の粒度では実態より少なく見える

以下は **ホットペッパーというプラットフォーム自体の仕様・落とし穴**。店舗が変わっても再現する。

### ★ レポートの価格は「定価」。客が払う価格は実ページにしかない

Salon Report のクーポン名に入っている金額（例 `￥22330→`）は
**取り消し線の左側＝定価**であって、新規客が実際に払う金額ではないことが多い。
実ページには**常設の「新規お試し価格」**が別に出ているケースがあり、定価より1〜2割ほど安いことがある。

- `hpb_coupon_stats.price_yen` = 定価、`hpb_coupon_stats.actual_price_yen` = 実売価格（実ページ由来）
- **価格帯の分析は必ず `actual_price_yen` で行う。** 定価で数えると帯が丸ごとずれる
- レポートと実ページの価格差だけを見て「値下げされた」と判断してはいけない。
  **元から併存している表示形態**であることが多く、割引率が一律に近ければそれは通常の掲載

### ★ クーポンが消えていても施策の失敗とは限らない

季節商材のクーポンは**商材の提供終了とともに落ちる**ことがある。
消失を見つけたら、効果不振と決めつける前にまず**商材・期間の都合ではないか**をオーナーに確認すること。

### ★ 口コミ依頼の自動配信機能は無いことが多い

ホットペッパーには口コミ依頼メールの自動配信機能が無いのが基本。
口コミを増やす手段は **会計時の対面依頼** と **サロンボードのメッセージ配信（手動）** が中心になる。
「自動で回す」前提の施策は立てられないことが多いので、**人手の手順を固定する**方向で設計すること。

### ★ `hpb_coupon_stats` に「無い」＝ 掲載が無い、ではない

`hpb_coupon_stats` は Salon Report 由来で、**予約実績のあるクーポンしか載っていない**。
「ある価格帯にクーポンが無い＝空白」と読むと誤る。正しくは「**その帯に予約が付いていない**」可能性があり、
実ページには掲載されていることがある。**掲載の有無を語るときは必ず実ページ（`page_observations`）で確認する。**

同じ理由で、`hpb_coupon_stats` が未取込の月は「予約ゼロのクーポンを非公開にする」系の提案は
**対象を特定できない**。先に集計を通すこと。

### ★ 口コミ一覧の先頭は「最新」ではないことがある

ホットペッパーの口コミ一覧は**投稿日の降順に並んでいないことがある**。
**先頭の日付を最新だと思って読むと誤る。** 「最終更新はいつか」を判定するときは、必ず**全件の投稿日を取って最大値**を取ること。

**数字が正常でも中身が壊れていることがある。** だから戦略は必ず**2系統**で立てる:

1. **レポート起点** — price / creative / ops の3担当が数字から
2. **実ページ起点** — page-scout が事実を記録し、strategist-page がそれを根拠に

統合担当はこの両方を採点対象にする。実ページの事実とレポートの数字が食い違っていたら、
**その食い違い自体が最大の論点**になる。

`page_observations` には**事実だけ**を書き、解釈は findings、施策は strategy_options に分ける。
観察が2週間以上古い場合は、それを根拠に提案してはいけない（実ページは日々変わる）。

## データソース — 役割が違うので全部使う

| ファイル | 入手元 | 強み | 弱み |
|---|---|---|---|
| **Salon Report PDF** | サロンボードから**いつでも自分でDL可** | 明細が細かい（ブログ別・特集別・クーポン別・スタイル別・スタイリスト別の実績）。テキスト層ありで**全自動抽出**できる | 新規/リピート別の売上・客単価がない。競合・口コミ・残キャパが分からない |
| **リボンPDF** | HPB担当者に依頼（画像・パスワード保護あり） | **新規客単価**（初回回収率に必須）、競合サロン個別、口コミ評点の内訳、残キャパ、クーポンラベル構成、最終口コミ更新日 | 依頼しないと出ない。手動＋画像読解が必要 |
| **実ページ** | `beauty.hotpepper.jp/sln<hpb_cd>/` を WebFetch | **お客さんが実際に見ている中身**。いつでも取れて無料 | 数値の推移は分からない。「今」しか見えない |
| CSV | サロンボード「CSV出力」 | 数値の裏取り | 明細は乏しい |

**使い分け**: Salon Report を毎月（＋月中の中間チェック）、リボンは**四半期に1回**で十分。

比較エリアが違う点に注意: **Salon Report＝中エリア／リボン＝小エリア**。同じCVRでも比較相手が違うので、平均値を混ぜてはいけない。

- ファイル名の下4桁が月号（例 `2606` = 2026年6月号）。**inboxに入れる前に月号を確認すること。**
  過去月のPDFを中間チェックに掛けると、確定月の月間実績を「今月ここまで」として記録してしまう
- 新規/リピート別の売上・客単価は **リボンPDFにしかない**（集計担当が入れる）
- リボンPDFは**パスワード保護されている場合がある**。その場合は担当者に確認する

### ★ 集計期間が2種類あることに注意

同じ `month` キーでも、値によって集計期間が違う。**取り違えると因果を読み違える。**

| 期間 | 範囲 | 該当する値 |
|---|---|---|
| **暦月**（calendar） | 1日〜月末 | 予約数・売上・客単価・新規/リピーター・指名・性別/年齢・新規リピート率、**リボンPDF由来の全指標** |
| **月号**（issue） | 最終木曜締め | 総PV・サロン情報PV・クーポンメニューPV・予約完了PV・**CVR・ACR**、ブログ/口コミ/スタイルの件数と閲覧数 |

- リボンは**暦月**なので、Salon Report の**予約データとは揃う**が、**PV/CVR/ACRとは約1週間ずれる**
- 「ブログを増やしたら予約が増えた」のような因果を語るときは、このズレを必ず明記する
- `hpb_ribbon_metrics` / `hpb_competitor_stats` には `period_type` 列で期間種別を保持している

## ★「エリア平均」の落とし穴（必ず守る）

Salon Report の「エリア平均」は **同じ中エリア・<u>同じ掲載プラン</u>のサロンの平均**。
つまり **プランを変えると比較相手そのものが入れ替わる**。

- 表記は必ず「**同エリア・同プラン平均**」とする（単に「エリア平均」と書かない）
- **プラン変更をまたぐ「対平均比」の増減を実力の変化として語らない**
- またぐ場合は **前年同月比 or 絶対値（新規獲得数・CPA・限界利益）** で判断する
- 分析手法 `exposure_benchmark_shift` がこの検知を担当

## レポートの方針 — 開いて楽しい画面にする

読むのは経営者であって、アナリストではない。**数字が並んでいるだけの画面は疲れるし、続かない。**

- レポート担当は、担当アシスタント **「ハナ」が話しかける形**で書く（各セクションの `hana` フィールド）
- 各セクションは「ハナのひとこと → その根拠となる数字」の順に置く
- 口調は丁寧だけど親しみやすく。絵文字は1文に1つまで
- **セリフは必ずDBの値から組み立てる。雰囲気で書かない。**
- 悪い数字はやわらかく、しかしごまかさずに。「〜が足りていません。ただ今日中に手を打てます」の形
- グラフは管理画面が `hpb_monthly_kpi` から描く。レポート担当は文章と表（Markdown）だけを書く

## 規約

- 金額の単位に注意: 売上は**万円**、客単価・CPAは**円**
- 処理済みの入力ファイルは `data/hpb/<store>/archive/<YYYYMM>/` へ移動（`data/` はGit管理外）
- 専門用語（CVR・ACR・CPA）には必ず一言の説明を添える
- **他店舗の追加**:
  1. `scripts/hpb/config.json` の `stores` に1エントリ追加する
     （`name` / `genre` / `hpb_cd` / `area` / `sub_area` / `seats` / `plan_cost_yen` / `variable_cost_rate` など）
  2. `data/hpb/<store>/{inbox,archive}` を作成する
  3. `python scripts/hpb/db_migrate.py` を実行し、`stores` テーブルへ登録する
  4. ネイル・エステなどレポート様式が異なる業態は `extract_content.py` の列定義の調整が必要
- **店舗ごとに得られた「実ページの落とし穴」「口コミ・クーポン運用の制約」などの発見は、
  そのサロンに固有の事実として `findings` / `page_observations` に書く。**
  本ファイルにはプラットフォーム共通の一般則だけを書き足す
- **このDBの実売上・掲載料などの数値を、公開サイト側のコード・seed・文言に転記しない**（AGENTS.md の絶対ルール）
