# GA4週次分析

毎週月曜 09:15（`scripts/site/run-weekly.ps1`）。事実の取得は `scripts/site/analyze.py`、解釈と所見は ga4-analyst。

## 読み方の原則
- 最重要KPIは **LINEクリック率（LINEクリック ÷ 訪問）**。訪問数ではなく率で入口とページを比べる。
- 訪問が1日数件の規模。10訪問未満の行の率、LINE合計10件未満の差は「参考」扱い。
- 流入元の見方: `google_business_profile / organic`＝Googleマップ・検索の店舗情報、`umbrella-no9.net / referral`＝旧サイト、
  `instagram / social`・`threads / social`＝SNS、`(direct)`＝URL直打ち・ブックマーク（SNSのアプリ内ブラウザもここに入ることがある）。
- 「入口の質」（その入口から来た人がLINEを押す率）と「入口の量」（訪問数）を分けて考え、伸ばす先を決める:
  率が高く量が少ない入口を増やす／量が多く率が低い入口の受け皿（ページ）を直す。

## 実験案の書き方（登録は人）
「何を変える／どのページ／何の指標がどうなるはず／何日見る」を1行ずつ。偽の希少性・価格の未確定表示・医療的断定は禁止（AGENTS.md の絶対ルール）。

## レポートの型（オーナー向け。読むのは月曜の朝の2〜3分）
`summary_md` は結論だけ（3〜4行）。`sections` はこの順で、各セクション短く:
1. **今週の数字** … 訪問・LINEクリック・率を前期間と比べた表（件数つき。少数は「参考」）
2. **うまくいっていること** … 伸びている入口・ページと根拠
3. **課題** … 率が低い入口・ページ、数字が示す離脱ポイント。原因の断定はしない
4. **次に試すこと** … 実験案を優先順に最大3つ（何を／どこで／指標／何日見る）。登録は人
5. **あなたにお願いしたいこと** … 人にしかできない作業だけ（0〜3件。例: GA4のキーイベント登録。無ければ「なし」）
6. **データの注意** … 少数・取り込みの遅れ・計測の未設定など
先週のレポートがあれば（`db_put` ではなく analyze.py の末尾の所見を参照）、前回の実験案がどうなったかを1行で触れる。

## 出力先
- **週次レポート: `db_put.py --report --channel ga4 --month <YYYY-Www>`（`/admin/ga4/report`。主な成果物）**
- 所見: `db_put.py --finding --channel ga4`（`/admin/ga4` に出る）
- 要約: Discord 1通（レポートのURL付き）
- 振り返り: `reflect.py add`
